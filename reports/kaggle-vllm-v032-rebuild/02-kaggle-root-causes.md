# Kaggle diagnostic root causes

The latest supplied diagnostic is CPython `/usr/bin/python3.12` 3.12.13 with SDK `0.3.3.dev0`, Torch `2.10.0+cu128`, Triton `3.6.0`, and **no installed vLLM distribution**. The direct `ModuleNotFoundError: No module named 'vllm'` establishes an installation/selection gap in that process. It does not establish a defect in the P31 native wheel. An earlier session reportedly installed 205 offline wheels, Torch 2.13+cu129, Triton 3.7.1 and native extensions; session identity and kernel/interpreter selection must be kept distinct.

The required evidence ladder is: wheel visible in Input → installed under `/usr/bin/python3.12` → imported by that interpreter → native extensions imported → engine initialized → four TP workers initialized → real Gemma 4 generation. Each level requires separate evidence. A cp312 subprocess cannot make a Python 3.13 notebook kernel import the same modules; call `/usr/bin/python3.12` explicitly. CUDA 12.8 Torch and CUDA 12.9 dependency wheels cannot be accepted as the pinned stack. Missing mounts, missing helper scripts and stale `/tmp` paths are installation failures, not GPU results. Fresh-session acceptance must check exact SDK and artifact identities.

The previous `llm.py` collapsed lazy `vllm.LLM` failures into a generic installation error. The new wrapper distinguishes absent top-level `vllm` from nested optional dependency, ABI, or lazy import failures, includes the original exception text and chains the exception. Global mode validates the installed stack before constructing the LLM; managed mode remains the default.
